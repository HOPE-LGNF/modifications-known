# 自动更新与一键更新可行性

## 结论

- **自动检查更新**：可行，成本低，建议先做。
- **一键更新已托管模组**：技术可行，但必须建立在安装清单、备份/回滚和来源记录之上；不建议直接覆盖现有包。
- **对未托管模组自动更新**：不建议；没有文件所有权和旧版本记录，无法安全替换或回滚。

## 当前实现（0.7 预览）

- 已安装页“检查更新”按钮：只对已关联 Nexus 的包调用 `GetModAsync`，比较最新版本与包版本，命中时显示“可更新 vX”徽标与摘要；手动触发，无后台轮询。
- 从模组发现下载最新版本时：
  - 先扫描已安装包并按 Nexus game-scoped id / 目录名 / 名称匹配；
  - 已安装版本不低于目标版本 → 跳过并提示；
  - 旧版本 → 确认后先把旧包移动到**同盘**的暂存目录（跨卷不会失败），再安装新版本；
  - “备份旧版本”可在确认框中关闭；勾选时会将暂存目录复制到
    `%APPDATA%\ModificationsKnown\backups\<时间>\<包名>`（复制支持跨卷）；
  - 新版本安装失败会删除半成品并移回暂存目录。
- 免费账号 NXM 下载同样走这套更新流程。
- 已安装页支持单项“更新到 vX”和“一键更新”：依次获取最新文件与直链、下载、替换；
  免费账号拿不到直链时会打开对应 Nexus 页面并跳过该项，其余继续。
- 仍没有后台自动更新；一键更新只处理已勾选/已检测到可更新的包。

## 自动检查（只读）

已有基础：

- `manifest.json` 中的 `source` 保存 Nexus `gameScopedId`、`modUid`、`fileId` 和安装版本；
- `NexusModsClient` 能获取模组详情、文件和版本；
- 已安装页已有来源显示。

实现方式：

1. 只检查状态为 `已托管` 且有 Nexus 来源的包；
2. 用 `GetModAsync`/文件列表比较最新版本与 manifest 中记录；
3. 在已安装列表中显示 `可更新` 徽标；
4. 由用户点击“检查更新”触发，不做后台轮询；
5. 缓存检查结果，遵守 Nexus API 配额（免费 100/小时、2500/天）。

预计：1–2 天。

风险：

- Nexus 的“最新版本”不一定适合当前游戏版本；
- 免费账号下载仍需 NXM，不能把“有更新”直接等同于“可一键下载”；
- 版本字符串可能不规范，需要以 file/version id 为主，字符串只做展示。

## 一键更新

前置条件：

- 旧包 manifest 和文件哈希；
- 备份旧文件/旧 manifest；
- 冲突预检（目标目录、依赖、用户修改）；
- 暂存新版本 → 写新 manifest → 原子替换 → 失败可恢复；
- 用户确认，不能静默覆盖。

建议流程：

```text
检查更新 → 显示版本差异
→ 下载新归档（NXM 或 Premium）
→ 解压到暂存目录
→ 校验新包布局
→ 备份旧包（文件 + manifest）
→ Directory.Move 旧包到 backup
→ Directory.Move 新包到目标
→ 写更新记录
```

如果旧包存在用户修改/新增文件：

- 默认阻止自动更新；
- 提示用户先导出或选择“保留用户文件”；
- 不做猜测性合并。

预计：1–2 周做到可用；再花 1 周打磨失败回滚和 UI。

## 不建议现在做的原因

- 当前安装器仍拒绝覆盖已有包；
- 还没有备份/回滚；
- 没有依赖变更检查；
- 免费账号的一键下载依赖 NXM 授权；
- 游戏正式版尚未发布，文件布局/兼容性可能变化。

## 推荐顺序

1. `可更新` 检查（只读）；
2. 备份/回滚；
3. 仅对“已托管 + 未修改 + 来源明确”的包提供一键更新；
4. 最后再考虑自动安装；默认仍应要求用户确认。
